## 1. Feature Name & Executive Summary

**Feature Name:** Interactive Effects

**Summary:**  
Interactive effects are how different pieces of equipments or conditions interact with each other when installed in the same building. The model itself does not do building by building simulations but a market wide adoption simulation. Therefore this process is a simplification of what might be happening at the building level. We assign each equipment or condition to an interaction_group and that determines how the savings of that measure might be adjusted based on what other equipment is installed in the market. We will average the effects across the entire count of each installed equipment/condition rather than have multiple version of the same condition with different levels of savings. This average change will be calculated in the code during the measure creation process. THe measure creation process is when the inputs from the workpapers (condition characterization) are read in and measures which are a comparison of two conditions (delta savings and delta costs) are created. this delta savings after creation will be adjusted based on the factors from the interactions input sheet. the interactions input sheet is a list of the interactions_groups and a percentage that the savings needs to be reduced by due to the interactions of the equipment within the group: Ex. insulation will reduce the savings generated by heating equipment, but a more efficient heating equipment will also reduce the savings upgrade insulation can expect to have. 
In version one we will just have a single input that reduces all the relevant measures based on the interaction_group. that percentage will be applied evenly to all conditions/equipment in that interactions group.

## 2. Business Justification / Problem Statement

### Current Problem
Equipment savings generated depends on the other equipment installed in a building. We do not want to model every individual possible equipment combination for every building so we will make an SME backed estimation of the average for that building type and this service territory (input for each study will be different based on baseline study data). 

### Business Impact
- **Complexity:** Adds one additional calculation loop in the measure creation process, but dictionary can be cached for reuse
- **User Impact:** SME must fill out two additional fields in workpapers (interaction_group, interaction_group_type) and a new 01_interaction_strength.xlsx input file
- **Model Accuracy:** Interactive effects are a crucial part of this modeling process, improving accuracy of savings estimates for measures that interact (e.g., insulation reducing HVAC savings)
- **Stakeholder Value:** Provides more realistic savings projections by accounting for real-world equipment interactions

### User Stories
- **As an** analyst, **I need to** model interactive effects between equipment types, **so that** savings estimates reflect real-world building physics
- **As an** SME, **I need to** specify which equipment groups interact and by how much, **so that** model accurately represents my territory's characteristics
- **As a** stakeholder, **I need to** see how interactive effects change savings projections, **so that** I can make informed program planning decisions

### Success Criteria
- Measures assigned to interaction groups have savings adjusted by specified interaction strength percentages
- Interaction effects QC report shows before/after savings comparisons for all affected measures
- Analyst can reproduce physics-based interaction calculations manually from QC outputs
- System correctly identifies effector vs effected measures and applies adjustments only to effected measures

## 3. Inputs

### Data Sources

#### Input Source 1: workpapers.xlsx
- **Sheet/Location:** Each condition sheet (dynamic sheets created per measure)
- **Required Fields:**
  - `interactions_group` (str, dropdown validation, optional)
    - Description: Predefined list of interaction groups that define which equipment types interact with each other. User selects from dropdown to assign conditions to groups.
    - Example values: `space_heating`, `space_cooling`, `water_heating`, `envelope`, `lighting`, `none`
    - Default: `none` (no interactions)
  - `interactions_group_type` (str, dropdown validation: "effector" or "effected", required if interactions_group is not "none")
    - Description: Defines whether this condition effects the savings of other measures ("effector") or if it is effected by other measures ("effected"). Some equipment can be both - this would be handled by adding the condition to multiple groups with different types.
    - Example values: `effector`, `effected`
    - Validation: Required if interactions_group is not "none"

- **Validation Rules:**
  - Data validation dropdowns enforced in Excel template for both fields
  - Predefined interaction_groups are hard-coded in template creation (000_Template_Creation.ipynb)
  - If interactions_group is "none", interactions_group_type can be blank
  - Cannot have interactions_group_type without an interactions_group

#### Input Source 2: 001_input/01_interaction_strength.xlsx
- **Sheet/Location:** Main sheet - created after workpapers filled out and is a list of conditions that have interaction groups 
- **Required Fields:**
  `condition_name` (str, populatied from workpapers that have interaction_groups filled out)
    - Description: created durign phase 1 template creation process

  `interaction_group` (str, must match predefined groups)
    - Description: The interaction group this strength applies to (e.g., space_heating, envelope)
    - Example values: `space_heating`, `water_heating`, `envelope`
    - this value is prepopulated  during the template creation process to have the relevant interaction group for each condition
  `interaction_group_type` (str, from workpapers df)
    - this value is prepopulated  during the template creation process to have the relevant interaction group for each condition
  `strength_of_effect` (float, 0.0 to 1.0, represents percentage)
    - Description: Physics-based percentage reduction in savings for effected measures due to presence of effector measures. For example, 0.15 means effected measures have 15% reduction in savings when effector is present.
    - Example values: `0.15` (15% reduction), `0.25` (25% reduction)
    - Validation: Must be between 0.0 and 1.0

- **Validation Rules:**
  - interaction_group values must exist in the predefined list from workpapers
  - strength_of_effect must be numeric, between 0 and 1
  - Each interaction_group should have entries defining interactions between effectors and effected types

### Assumptions
- Initial market counts (saturation) from market characterization (001_Market_Characterization.ipynb) will be used to estimate overlap between effector and effected measures
- Interaction effects are applied uniformly across all building types within an interaction group (Phase 1)
- Interaction strength is based on SME input reflecting technical reference manual (TRM) guidance and known physics
- Interactions are calculated at the population level using cross-multiplication of saturations to estimate overlap
- For Phase 1, interaction effects are static (calculated once during measure creation). Future phases may incorporate dynamic interactions that change with adoption over time
- Incremental cost changes due to interactions are negligible and not modeled (confirmed by Griff)

## 5. Technical Specifications

### Algorithm / Logic Description

#### High-Level Flow
1. Read interaction_group assignments from workpapers for all conditions
2. Load interaction strength matrix from 01_interaction_strength.xlsx
3. Pull initial market counts for all conditions from market characterization results
4. Calculate overlap factors between effector and effected measures within each interaction group
5. Apply interaction adjustments to savings of effected measures in assembled_measures
6. Generate QC reports showing before/after comparisons

#### Detailed Logic Phase 3

**Step 1: Load and Validate Interaction Data**
```python
Pseudocode:
  # Load interaction assignments from workpapers
  FOR each condition_sheet in workpapers:
    READ interaction_group, interaction_group_type
    STORE in conditions_dict[condition_name] = {
      'interaction_group': value,
      'group_type': value,
      'initial_count': from market characterization
    }
  
  # Load interaction strength matrix
  READ 01_interaction_strength.xlsx
  VALIDATE all interaction_groups exist in predefined list
  VALIDATE strength_of_effect values are between 0 and 1
  
  # Create lookup: interaction_strength[group][effector_type][effected_type] = strength
```
- **Inputs:** workpapers.xlsx (all condition sheets), 01_interaction_strength.xlsx, market characterization counts
- **Outputs:** conditions_dict with interaction metadata, interaction_strength lookup table
- **Edge Cases:** 
  - Condition has no interaction_group: treat as "none", no adjustments
  - Interaction group not in strength file: log warning, skip adjustments for that group
  - Missing initial counts: use 0 (no overlap)

**Step 2: Calculate Overlap Factors**
```python
Formula:
  overlap_factor = (count_effector / total_market_count) × overlap_assumption
  
  Where:
    count_effector = sum of initial counts for all effector conditions in group
    total_market_count = total addressable market for that building type
    overlap_assumption = 1.0 for Phase 1 (assume random distribution)
    
  # For each effected measure:
  FOR each measure WHERE interaction_group_type == 'effected':
    group = measure.interaction_group
    
    # Find all effectors in same group
    effectors_in_group = [c for c in conditions WHERE 
                          c.interaction_group == group AND 
                          c.interaction_group_type == 'effector']
    
    # Calculate total effector presence in market
    total_effector_count = SUM(effector.initial_count for effector in effectors_in_group)
    market_size = get_market_size(measure.building_type, measure.market)
    
    overlap_factor[measure] = total_effector_count / market_size
    # Cap at 1.0 (100% overlap)
    overlap_factor[measure] = MIN(overlap_factor[measure], 1.0)
```
- **Inputs:** conditions_dict with initial counts, building type market sizes
- **Outputs:** overlap_factor for each effected measure (0.0 to 1.0)
- **Edge Cases:** 
  - Market size is 0: set overlap_factor = 0
  - No effectors in group: set overlap_factor = 0 (no interaction)
  - Effector count > market size: cap overlap at 1.0 * important thought here

**Step 3: Apply Interaction Adjustments to Savings**
```python
Formula:
  adjusted_savings = original_savings × (1 - overlap_factor × strength_of_effect)
  
  Where:
    overlap_factor = calculated in Step 2
    strength_of_effect = lookup from interaction_strength file
    
Pseudocode:
  FOR each measure in assembled_measures:
    IF measure.interaction_group_type == 'effected':
      overlap = overlap_factor[measure]
      strength = interaction_strength[measure.interaction_group]
      
      # Apply to all savings columns
      measure.kwh_savings_adjusted = measure.kwh_savings × (1 - overlap × strength)
      measure.therm_savings_adjusted = measure.therm_savings × (1 - overlap × strength)
      measure.mmbtu_savings_adjusted = measure.mmbtu_savings × (1 - overlap × strength)
      
      # Track adjustment for QC
      qc_record = {
        'measure': measure.name,
        'original_kwh': measure.kwh_savings,
        'adjusted_kwh': measure.kwh_savings_adjusted,
        'adjustment_pct': overlap × strength × 100,
        'overlap_factor': overlap,
        'strength_of_effect': strength
      }
      qc_records.append(qc_record)
```
- **Inputs:** assembled_measures (pre-adjustment), overlap_factor dict, interaction_strength lookup
- **Outputs:** assembled_measures with adjusted savings, qc_records list
- **Edge Cases:**
  - Savings is 0 or negative: apply adjustment anyway (proportional)
  - Multiple interaction groups: handle each independently (future enhancement for compounding effects)
  - Effector measures: no adjustment applied (adjustment_pct = 0)

### Performance Considerations
- **Expected Runtime:** ~2-10 seconds for typical dataset (5000-20000 measures)

  - Consider vectorized pandas operations for savings adjustments instead of row-by-row

## 10. Open Questions & Decisions

### Open Questions

**Q1: Should interactions be recalculated annually in the adoption model?**
- **Context:** Phase 1 calculates interactions once using initial market counts. As adoption progresses, actual overlap changes (e.g., if insulation adoption increases, HVAC savings reduction should increase). Recalculating yearly would be more accurate but adds computational cost.
- **Options:** 
  - Option A: Keep static for Phase 1, defer to Phase 2
  - Option B: Implement dynamic recalculation immediately in 030_Yearly_Full_Adoption_Model
- **Decision Needed By:** 2026-01-31 (technical review)
- **Owner:** Mike Fink (technical lead)
- **Status:** 🔴 Open

**Q2: How to handle measures in multiple interaction groups?**
- **Context:** Some equipment could logically belong to multiple groups (e.g., heat pump affects both heating and cooling). Current design assumes one group per measure.
- **Options:**
  - Option A: Force user to choose primary group only
  - Option B: Allow comma-separated groups, apply both adjustments
  - Option C: Defer to Phase 2, keep simple for Phase 1
- **Decision Needed By:** 2026-01-31 (design review)
- **Owner:** Matt (SME)
- **Status:** 🔴 Open

**Q3: Should overlap assumption be adjustable by user?**
- **Context:** Phase 1 assumes random distribution (overlap = effector_saturation / market_size). Some programs have known correlation (e.g., weatherization + electrification often paired). Should we allow SME to adjust overlap assumption?
- **Options:**
  - Option A: Keep simple, assume random distribution
  - Option B: Add "correlation_factor" field to strength file (1.0 = random, 2.0 = twice as likely)
  - Option C: Add separate correlated_programs input sheet
- **Decision Needed By:** 2026-02-05 (before Phase 3 implementation)
- **Owner:** Matt (SME)
- **Status:** 🔴 Open

**Q4: Should effector measures ever be adjusted themselves?**
- **Context:** Current design: effectors reduce others' savings but are not themselves adjusted. In reality, bidirectional effects exist (insulation reduces HVAC savings, efficient HVAC reduces insulation savings).
- **Options:**
  - Option A: Keep one-directional for Phase 1 simplicity
  - Option B: Allow measures to be both effector and effected (assign to two groups with different types)
  - Option C: Add "bidirectional" flag to strength file
- **Decision Needed By:** 2026-01-31 (design review)
- **Owner:** Cliff & Griff (design advisors)
- **Status:** 🔴 Open

### Decisions Made

**✅ D1: Static Interactions for Phase 1** (Date: 2026-01-30 - tentative pending review)
- **Decision:** Implement interactions as one-time calculation during measure creation, not dynamically in adoption model
- **Rationale:** Simpler implementation, faster execution, sufficient accuracy for initial phase. Can enhance in Phase 2 if needed.
- **Alternatives Considered:** Dynamic yearly recalculation (deferred to Phase 2)
- **Approved By:** Pending Mike Fink approval (technical review 1/27)
- **Impact:** Reduces computational complexity, speeds up development timeline

**✅ D2: No Incremental Cost Adjustments** (Date: 2026-01-30)
- **Decision:** Interaction effects apply only to savings, not to incremental costs
- **Rationale:** Cost interactions are rare and small magnitude per Griff's confirmation. Adding cost adjustments would complicate significantly for minimal accuracy gain.
- **Alternatives Considered:** Adding cost adjustment factors (rejected as unnecessary)
- **Approved By:** Griff (advisor)
- **Impact:** Simplifies implementation, reduces input burden on SME

## Appendix

### Glossary
- **Interaction Group:** A predefined category of equipment/conditions that interact with each other (e.g., space_heating, envelope, water_heating)
- **Effector:** A condition/measure that reduces the savings potential of other measures (e.g., insulation is an effector that reduces HVAC savings)
- **Effected:** A condition/measure whose savings are reduced by the presence of effectors (e.g., HVAC equipment is effected by envelope improvements)
- **Strength of Effect:** The percentage by which an effector reduces an effected measure's savings (e.g., 0.15 = 15% reduction)
- **Overlap Factor:** The estimated proportion of the market where both effector and effected measures are present (calculated from initial saturation counts)
- **Condition:** A specific state of equipment or building characteristic (e.g., "electric_resistance_heat", "air_source_heat_pump", "r38_insulation")
- **Measure:** A comparison between two conditions representing an upgrade/improvement (e.g., measure = condition_to - condition_from)
- **Assembled Measures:** The output file containing all possible measure comparisons with calculated savings and costs
- **Market Characterization:** The initial process (001_Market_Characterization.ipynb) that determines baseline equipment counts and saturations
- **TRM (Technical Reference Manual):** Industry-standard documentation defining energy savings calculation methodologies and interaction effects

### Examples

**Example 1: Space Heating Interaction**

Scenario:
- Interaction Group: `space_heating`
- Effector: Ceiling insulation upgrade (R19 → R38)
- Effected: Heating system upgrade (electric resistance → heat pump)
- Strength of Effect: 0.20 (20% reduction)
- Initial Market: 10,000 single-family homes
- Current R38 saturation: 3,000 homes (30%)

Calculation:
- Overlap Factor = 3,000 / 10,000 = 0.30
- Heat pump measure original savings: 5,000 kWh/year
- Adjustment = 1 - (0.30 × 0.20) = 1 - 0.06 = 0.94
- Adjusted savings = 5,000 × 0.94 = 4,700 kWh/year
- Savings reduction = 300 kWh/year (6%)

Interpretation: In a market where 30% of homes already have R38 insulation, heating equipment upgrades save 6% less energy because better insulation reduces heating loads.

**Example 2: No Interaction**

Scenario:
- Measure: Lighting upgrade (LED)
- Interaction Group: `none`
- Overlap Factor: N/A
- Adjustment: 1.0 (no adjustment)
- Original savings = Adjusted savings

Interpretation: Lighting measures assigned to "none" group are not affected by any interactions.
